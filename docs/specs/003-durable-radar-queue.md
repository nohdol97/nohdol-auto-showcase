# 스펙 003: 중단되지 않는 Radar 후보 분석

- 상태: active
- 날짜: 2026-09-06
- 관련 ADR: `docs/adr/002-radar-queue-processing.md`

## 문제

수동 Radar 실행은 HTTP 응답을 즉시 반환한 뒤 전체 장소 검색과 후보 분석을 `ctx.waitUntil()`에서 수행한다. 운영 첫 실행에서 후보 두 곳은 저장됐지만 30초 안에 전체 작업과 실행 집계 갱신이 끝나지 않아, 실행이 `running · 0곳 분석`에 남고 화면과 다음 실행이 영구적으로 잠겼다.

## 목표

1. 최대 10곳의 후보 분석이 관리자 화면을 닫아도 중단되지 않게 한다.
2. 각 후보가 저장될 때 실행 진행 수를 갱신하고, 모든 후보의 성공·실패가 확정되면 실행을 종료한다.
3. Queue의 중복 전달과 일시적인 OpenAI 실패를 안전하게 처리한다.
4. 예기치 않게 진전이 끊긴 실행도 다음 예약 정리에서 복구한다.

## 비목표

- 공개 장소·근거·연락처의 수집 범위 변경
- 업체 자동 연락 또는 외부 시스템의 최종 행동
- 여러 실행의 동시 처리나 실행 우선순위 UI
- 설치·제품키·문의 사용자 권한과 Radar 권한의 결합

## 요구사항

### R1. Queue 경계

수동·예약 실행은 D1에 실행 레코드를 만든 뒤 Kakao 장소 검색 결과를 `RADAR_QUEUE`에 후보별 메시지로 등록한다. 메시지에는 실행 ID와 스펙 002가 허용한 공개 장소 필드만 포함하고 비밀값, 개인 이름, 리뷰 본문은 포함하지 않는다. HTTP 실행 API는 Queue 등록 결과를 `202`로 반환하며 장시간 분석을 `ctx.waitUntil()`에 맡기지 않는다.

### R2. 권위 상태와 진행 집계

D1의 `radar_runs`와 `radar_candidates`가 권위 상태다. Queue 등록 전에 `places_found`를 확정하고 진행 시각을 남긴다. 후보 하나가 성공 또는 최종 실패로 저장될 때마다 성공 수와 전체 처리 수를 다시 계산한다. 전체 처리 수가 `places_found`에 도달하면 성공만 있으면 `completed`, 일부 실패면 `partial`, 전부 실패면 `failed`로 종료한다.

### R3. 중복 전달과 재시도

Queue의 최소 한 번 전달을 전제로 `(run_id, kakao_id)` 고유 제약을 멱등성 경계로 사용한다. 이미 저장된 후보 메시지는 모델을 다시 호출하지 않고 진행 상태만 재계산한다. 일시적인 처리 실패는 30초 간격으로 최대 세 번 시도하고, 세 번째 실패는 실패 후보로 저장한 뒤 메시지를 확인 처리한다.

### R4. 정체 실행 복구

`radar_runs`에 마지막 진행 시각을 저장한다. 실행 시작·Queue 등록·후보 저장 때마다 이를 갱신한다. 15분 이상 진전이 없는 `running` 실행은 저장된 후보를 집계하여, 후보가 있으면 `partial`, 없으면 `failed`로 종료하고 `RADAR_RUN_STALE` 오류 분류를 남긴다. 새 실행 전과 기존 5분 정리 작업에서 복구를 시도한다.

### R5. 화면 상태

실행 중과 종료 요약은 성공 분석 수와 발견한 전체 후보 수를 `2/3곳 분석`처럼 표시한다. Queue 등록이 끝난 뒤에는 화면을 닫아도 계속 처리된다는 안내를 유지한다. 정체 실행이 복구되면 버튼과 검색 설정을 다시 사용할 수 있다.

### R6. 보안·소유권 유지

Queue 생산과 소비는 기존 showcase Worker와 전용 `RADAR_QUEUE` 바인딩만 사용한다. Radar 관리자 인증, noindex/no-store, D1의 `radar_*` 분리, 공개 정보 범위, 자동 연락 금지, 설치·제품키 권한 부재는 변경하지 않는다.

### R7. 배포와 롤백

운영 Queue 이름은 `nohdol-auto-showcase-radar`로 고정한다. Queue 생성, D1 마이그레이션, Worker 배포를 각각 검증한다. Worker 롤백 시 D1의 추가 진행 시각 열과 Queue는 호환 가능한 비활성 리소스로 남기며, 삭제나 데이터 제거는 별도 승인을 받는다.

## 완료 기준

1. `[REG:radar.queue_delivery]` 테스트가 수동 API가 `waitUntil()` 없이 공개 장소 메시지를 Queue에 등록하고 발견 수를 저장하는지 검증한다.
2. `[REG:radar.queue_retry]` 테스트가 일시 실패 재시도, 세 번째 실패 기록, 개별 확인 처리를 검증한다.
3. `[REG:radar.queue_idempotency]` 테스트가 중복 메시지에서 모델 재호출 없이 종료 집계가 유지되는지 검증한다.
4. `[REG:radar.stale_recovery]` 테스트가 15분 이상 정체된 실행을 저장 후보 기준으로 복구하는지 검증한다.
5. `[REG:radar.admin_surface]` 테스트가 실행 중 진행 수와 Queue 후속 처리 문구를 검증한다.
6. `npm run verify`가 전체 테스트, 정적 빌드, Queue 바인딩을 포함한 Worker dry-run을 통과한다.
7. 운영 D1 마이그레이션, Queue 생산자·소비자 연결, 새 Worker 버전, 실제 3곳 실행의 종료 상태를 각각 확인한다.

## 미검증 범위

- Cloudflare가 문서화한 최소 한 번 전달 외의 정확히 한 번 전달 보장
- 외부 업체 페이지 내용의 지속적인 정확성
- 장기간 운영에서의 Queue 비용과 OpenAI 사용량 추이
